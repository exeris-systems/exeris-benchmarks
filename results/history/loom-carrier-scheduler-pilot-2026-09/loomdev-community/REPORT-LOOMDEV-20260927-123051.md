## 4. Draft Experience Report for loom-dev (Plain Text Skeleton)

```text
Subject: Experience report: custom VirtualThreadScheduler + pollerMode=3
         with an FFM-based POSIX transport

Hi,

I have been experimenting with the custom virtual thread scheduler support in
the loom repo (EA build 28-testing) in Exeris, an open JVM runtime whose Community
transport performs socket I/O via Panama FFM on raw POSIX fds, while readiness
delegates to java.nio.channels.Selector (which under pollerMode=3 attaches to the
carrier thread sub-poller). I am sharing results and API feedback as an external
data point outside Netty.

Setup
  AMD Ryzen 5 (6C/12T), Linux 7.0 generic. Carriers on physical CPUs 2, 3 (SMT siblings
  8, 9 idle). Rest of JVM (Master Poller, GC, JIT) on CPUs 0, 1, 6, 7. Load generator
  isolated on CPUs 4, 5, 10, 11. Plain HTTP/1.1 GET /plaintext, 100 connections,
  interleaved fresh-JVM runs; medians shown.

Scheduler
  Per-carrier MPSC queue, no work-stealing, carriers pinned via sched_setaffinity,
  read sub-pollers kept on their carrier under pollerMode=3.

Results (median [min-max])
  A  FJP, default poller, parallelism=2          233363.1 [233363.1 - 233363.1] req/s, p99: 413.95 ms [413.95 ms - 413.95 ms]
  B  FJP, pollerMode=3, parallelism=2            253480.4 [253480.4 - 253480.4] req/s, p99: 240.22 ms [240.22 ms - 240.22 ms]
  C  custom scheduler, pollerMode=3 (floating)   248942.9 [248942.9 - 248942.9] req/s, p99: 2.02 ms [2.02 ms - 2.02 ms]
  D  custom scheduler, pollerMode=3 (pinned 2,3) 226008.2 [226008.2 - 226008.2] req/s, p99: 1.21 ms [1.21 ms - 1.21 ms]
  E  custom scheduler, pollerMode=3 (N+1 budget)  223268.9 [223268.9 - 223268.9] req/s, p99: 1.70 ms [1.70 ms - 1.70 ms]

  The main effect is consistent with Francesco Nigro's observations on Netty
  (github.com/franz1981/Netty-VirtualThread-Scheduler/blob/master/PERFORMANCE.md):
  once carrier threads have dedicated CPU affinity and do not get descheduled
  by auxiliary threads, event notifications stop arriving in bursts and tail
  latency drops dramatically (p99 from 500ms+ down to ~1.3ms).

API Feedback
  - VThreadTask attachment: in stock Loom, VThreadTask.attach(), attachment(),
    and preferredCarrier() throw UnsupportedOperationException unless a custom
    scheduler is active. A supported interface for attaching per-vthread context
    or routing hints would avoid fragile reflection.
  - Poller lifecycle hooks: in pollerMode=3, sub-pollers are spawned implicitly.
    A first-class callback or builder hook in VirtualThreadScheduler to name,
    bind, or set CPU affinity for sub-poller threads would allow clean isolation.
  - Scheduler telemetry: VirtualThreadScheduler currently lacks standard methods
    to expose queue depth or carrier state to JFR or external monitoring.

Questions
  1. Are there plans to formalize the carrier-poller binding lifecycle in the
     public VirtualThreadScheduler SPI?
  2. Is preferredCarrier(CarrierThread) intended to become accessible to application
     dispatchers without internal reflection?

Thanks for making the scheduler pluggable.

Arkadiusz
```
