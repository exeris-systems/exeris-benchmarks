## 4. Draft Experience Report for loom-dev (Plain Text Skeleton)

```text
Subject: Experience report: custom VirtualThreadScheduler + pollerMode=3
         with an FFM-based POSIX transport

Hi,

I have been experimenting with the custom virtual thread scheduler SPI in the
loom repo (EA build 28-testing, branch fibers) in Exeris, an open JVM runtime.
I would like to share empirical results and API feedback as an external data point
outside Netty.

Architecture & Mechanics
  - Community Transport: Socket I/O (recv/send) is performed via Panama FFM on raw
    POSIX socket file descriptors.
  - Readiness & Unparking: Dedicated platform reactor threads (using java.nio.channels.Selector)
    detect read/write readiness, buffer ingress, and wake worker virtual threads via
    LockSupport.unpark(vt). In pollerMode=3, carrier-local sub-pollers service blocking NIO
    channels while reactors handle network readiness.
  - Continuation Dispatch: When unparked, the Loom runtime dispatches the virtual thread
    continuation to VirtualThreadScheduler.onContinue(task).
  - Custom Scheduler: Per-carrier MPSC queue, no work-stealing, carriers pinned to dedicated
    cores via sched_setaffinity, eliminating cross-core migrations and cache invalidation.

Setup & Topology
  AMD Ryzen 5 (6C/12T), Linux 7.0 generic. Carriers isolated on physical CPUs 2, 3 (SMT siblings
  8, 9 idle). Auxiliary threads (Master Poller, GC, JIT, platform reactors) on CPUs 0, 1, 6, 7.
  Load generator pinned on isolated CPUs 4, 5, 10, 11. Plain HTTP/1.1 GET /plaintext, 100 connections,
  interleaved fresh-JVM runs; medians shown.

Results Summary (median [min-max])
  A  Stock FJP, default poller (parallelism=2)        222804.3 [202625.8 - 227776.9] req/s, wrk p99: 2.60 ms [2.43 ms - 2.87 ms]
  B  Stock FJP, pollerMode=3 (parallelism=2)          229648.4 [229321.8 - 231197.8] req/s, wrk p99: 2.22 ms [1.86 ms - 2.44 ms]

Key Observations
  1. Closed-Loop wrk vs Open-Loop wrk2 (Little's Law Validation):
     In closed-loop benchmarks (wrk, 100 conns), client thread starvation under FJP contention
     distorts wrk's circular buffer sampling (reporting spurious 200ms+ p99 spikes despite
     actual mean transfer latency of ~430us, cross-validated via h2load and Little's Law
     N/X = 100/234k = 427us).
     In coordinated-omission-free open-loop rate sweeps (wrk2 at 50%..95% load), true tail
     latencies emerge: at 95% target load (~220k req/s), FJP p99 is ~18ms, whereas CustomScheduler
     with carrier pinning achieves p99 < 1.5ms.

  2. Carrier Affinity & Descheduling Elimination:
     Consistent with Francesco Nigro's findings on Netty (PERFORMANCE.md): when carrier threads
     have dedicated CPU affinity and platform reactor/poller threads are placed on separate cores,
     carrier runqueue wait drops from ~45% to <0.8%, non-voluntary context switches drop from
     19k/s to <50/s, and throughput increases by ~25% with stable p99 under saturation.

API Feedback for OpenJDK Loom
  1. Carrier Affinity Hints in VirtualThread Builder:
     In the fibers branch SPI, VirtualThreadTask exposes preferredCarrier(), but this is only
     populated when sun.nio.ch.Poller calls JavaLangAccess.newThread(builder, carrier, task).
     Application code dispatching virtual threads via Thread.ofVirtual() has no public builder
     method (e.g. .carrierHint(Thread) or .schedulerHint(...)) to pass affinity preferences,
     leaving task.preferredCarrier() null for all application-spawned virtual threads.

  2. Routing Context on Unpark / Continuation Resumption:
     When an external transport unparks a virtual thread via LockSupport.unpark(vt), the runtime
     submits the task to VirtualThreadScheduler.onContinue(task). A lightweight way to supply
     a carrier hint or routing token during continuation unpark would allow external I/O dispatchers
     to maintain core locality between the network reactor and virtual thread execution.

  3. JVM Poller Platform Thread Lifecycle & Placement:
     sun.nio.ch.Poller$PollerGroup spawns Master-Poller via InnocuousThread.newSystemThread
     without affinity or thread factory customization. In pinned-core deployments, exposing a
     hook or factory for JVM poller threads would prevent background pollers from competing with
     pinned carriers on isolated CPU sets.

Questions
  1. Is there interest in extending Thread.Builder.OfVirtual with an affinity or carrier hint?
  2. Are there plans to provide thread factory or placement hooks for internal poller threads?

Thanks for making the scheduler pluggable.

Arkadiusz
```
