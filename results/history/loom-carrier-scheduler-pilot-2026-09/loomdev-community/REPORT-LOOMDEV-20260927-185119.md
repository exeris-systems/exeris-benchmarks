## 2. Factor-by-Factor Empirical Delta Analysis

- **Factor 1 (A_iso vs A - Core Isolation of FJP):** Restricting FJP carriers to {2,3} away from network reactors and GC/JIT changes throughput by +9.1% (220909 vs 202566 req/s), p99: 4.01 ms vs 3.17 ms.
- **Factor 2 (C_iso vs A_iso - Scheduling Architecture without Stealing):** On identical dedicated cores {2,3}, replacing FJP work-stealing with dedicated per-carrier MPSC queues changes throughput by +12.0% (247404 vs 220909 req/s), p99: 3.14 ms vs 4.01 ms.
- **Factor 3 (D vs C_iso - 1:1 Carrier Pinning):** Adding 1:1 CPU affinity to the custom scheduler changes throughput by -1.6% (243429 vs 247404 req/s), p99: 3.18 ms vs 3.14 ms.
- **Overall (D vs A - Pinned Custom Scheduler vs Unconstrained Stock FJP):** Throughput: +20.2% (243429 vs 202566 req/s).

Subject: Experience report: Carrier locality with a custom VirtualThreadScheduler in an FFM POSIX transport

Hi Loom team,

I have been experimenting with the custom virtual thread scheduler SPI in the
loom repo (EA build 28-testing, branch fibers) in Exeris, an open JVM runtime.
I would like to share empirical results and API observations as an external data point
outside Netty.

Architecture & Mechanics
  - Community Transport: Socket ingress is performed via Panama FFM on raw POSIX socket
    file descriptors into off-heap MemorySegments. Dedicated platform reactor threads
    (using java.nio.channels.Selector) detect readiness and wake worker virtual threads
    via LockSupport.unpark(vt). Responses are written directly to the socket fd by the
    virtual thread on its carrier (falling back to reactor flush only on partial writes).
  - Continuation Dispatch: When unparked, the Loom runtime dispatches the continuation
    to VirtualThreadScheduler.onContinue(task).
  - Custom Scheduler: Dedicated MPSC queue per carrier (no work-stealing).

Setup & Topology
  AMD Ryzen 5 (6C/12T), Linux 7.0 generic. Carriers isolated on physical CPUs 2, 3
  (SMT siblings 8, 9 idle). Platform reactors pinned to CPUs 0, 1. Other JVM threads
  (GC, JIT) re-pinned to CPUs 0, 1, 6, 7 post-warmup. Load generator on CPUs 4, 5, 10, 11.
  Plain HTTP/1.1 GET /plaintext, 100 connections. Interleaved fresh-JVM runs; medians [min-max].

Configurations (All normalized to 2 carrier threads)

Observations
  1. Isolating Effects: Factorial Comparison:
     Comparing A vs A_iso isolates the effect of separating FJP carriers from network reactors
     and GC/JIT. Comparing A_iso vs C_iso isolates scheduling architecture (work-stealing vs
     per-carrier MPSC queues) on identical dedicated cores. Comparing C_iso vs D isolates
     1:1 carrier affinity pinning.
  2. Capacity Cliff vs Graceful Degradation:
     Below single-queue capacity (50% to 85% load), pinned carrier configurations provide
     repeatable, tight tail latencies. Near capacity (90% to 95%), single-queue accumulation
     creates a sharper latency cliff for pinned carriers, whereas floating configurations degrade
     more gradually across wider variance.

API Feedback for OpenJDK Loom
  1. Carrier Routing Hints in Thread.Builder.OfVirtual:
     VirtualThreadScheduler.newThread(builder, preferredCarrier, task) is public on the scheduler
     SPI, but application code creating virtual threads via Thread.ofVirtual() cannot specify
     a preferred carrier or routing tag without direct access to the custom scheduler instance.
     Exposing an affinity or carrier hint on Thread.Builder.OfVirtual would allow standard
     dispatchers to pass routing intent without custom scheduler coupling.

Questions
  1. Are there plans to expose carrier routing hints on Thread.Builder.OfVirtual?
  2. How do the Loom authors view the trade-off between floating work-stealing carriers and
     pinned single-queue carriers for network I/O workloads approaching capacity?

Thanks for making the scheduler pluggable.

Arkadiusz Przychocki
